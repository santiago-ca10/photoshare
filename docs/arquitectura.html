Flujos principales

Por dónde viaja cada acción del usuario.

Subir una foto

Escritura distribuida con invalidación de caché y aviso en vivo.

1Navegador
→
2Nginx
→
3Fotos (1 o 2)
→
4Volumen + PostgreSQL
→
5Redis
→
6Notificaciones
  1. El navegador envía POST /api/photos con la imagen y el token JWT.
  2. Nginx elige una réplica; esta valida token, tipo y tamaño.
  3. Guarda el archivo, inserta la fila en PostgreSQL y borra la caché del feed.
  4. Publica {type: photo} en Redis; Notificaciones lo reenvía por WebSocket.

Ver el feed

Lectura rápida: caché primero, base de datos si falla.

1Navegador
→
2Nginx
→
3Fotos (1 o 2)
→
4Redis
→
5PostgreSQL (si no hay caché)
  1. GET /api/photos/feed llega a una réplica elegida por round-robin.
  2. Si Redis tiene el feed responde de inmediato (cached: true).
  3. Si no, consulta PostgreSQL y guarda el resultado 30 segundos.
  4. La respuesta incluye served_by: así se ve qué réplica atendió.

Dar like

Concurrencia resuelta por la base de datos.

1Navegador
→
2Nginx
→
3Social
→
4PostgreSQL
→
5Redis → Notificaciones
  1. Social valida el JWT localmente, sin llamar a Auth.
  2. INSERT … ON CONFLICT DO NOTHING sobre la clave (user_id, photo_id): nunca hay duplicados.
  3. El contador se calcula con COUNT(*); no hay un número compartido que corromper.

Caída de una réplica

Tolerancia a fallos sin intervención.

1Navegador
→
2Nginx
→
✕photos-1 caída
→
3photos-2 responde
  1. Nginx detecta el fallo y aparta la réplica 10 segundos (max_fails=1 fail_timeout=10s).
  2. Las peticiones se reintentan en la otra réplica: el usuario no nota el cambio.

Conceptos demostrados

Lo que el sistema permite explicar y probar.

Balanceo de carga

Round-robin entre photos-1 y photos-2; visible en la barra superior de la interfaz.

Tolerancia a fallos

Si cae una réplica o Redis, el sistema sigue sirviendo.

Caché

Feed en Redis con TTL de 30 s e invalidación en cada cambio.

Concurrencia

Likes simultáneos protegidos por la clave primaria compuesta.

Mensajería Pub/Sub

Los servicios publican eventos sin conocer a quién los consume.

Tiempo real

WebSocket empuja avisos a todos los navegadores conectados.

Transparencia

El usuario ve una sola aplicación; no sabe cuántas piezas hay.

Escalabilidad horizontal

Servicios sin estado: se agregan réplicas al upstream de Nginx.

Puntos únicos de falla

Limitaciones conscientes y cómo mejorarlas.

Nginx

Si cae, todo es inaccesible. Mejora: varias instancias y un balanceador externo.

PostgreSQL

Una sola instancia. Mejora: replicación primaria/secundaria.

Volumen de fotos

Disco compartido único. Mejora: almacenamiento de objetos (MinIO / S3) + CDN.
